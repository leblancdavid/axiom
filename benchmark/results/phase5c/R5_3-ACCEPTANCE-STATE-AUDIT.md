## Sufficiency and boundary

The *effective prior composed acceptance state* is sufficient **provided it includes the R4/R5 suite overlay**, not just R5.2's capability-profile JSON: it has the exact active method IDs, superseded IDs, active replacement IDs, origins and replacement edges. Intersect the amendment's exact source/dimension declarations with the active assertions in this state. For an active affected assertion, replace its active carrier with a B17 carrier; for an inactive original, leave its earlier edge intact and follow the active replacement, if any. If the earlier amendment removed the behavior, there is no corresponding assertion to replace. Unaffected assertions remain active. This criterion is entirely a function of frozen achieved history, frozen prior acceptance disposition and frozen amendment metadata. It does not need a track identifier, source implementation, prediction, execution result or classification.

The current `superseded_cases` dictionary **alone is insufficient**: R4's B04/B07 skips and R5's 24 skips are computed by the runner and absent there, and method-level dispositions do not label independent assertions. The minimal extension must therefore materialize the already frozen effective acceptance overlay as explicit state with assertion/behavior identifiers and provenance before applying new acceptance transitions. It must not infer assertions from execution or silently assume an unlabelled method is wholly affected. This is representation of existing frozen acceptance plus prospective annotations, not a retroactive edit to any historical method or R5.2 artifact.

In particular, actor-required task mutations and role-bearing user results are distinct dimensions. Four active B01–B16 methods have both; all 33 B01–B16 and seven {B01,B04} methods have actor-affected task mutations (including `migrate`). The 28 old supersession skips and two B02 skips remain separate. An assertion-level rule must retain the B17 audit's unrelated assertions within each replaced method; a method-level runner may select a new carrier only after all assertions have been accounted for and verified against a pinned source/replacement inventory.
