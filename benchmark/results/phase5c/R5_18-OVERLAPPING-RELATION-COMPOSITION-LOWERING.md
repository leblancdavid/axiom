# R5.18 — Overlapping relation composition lowering (prospective, 2026-10-02)

## Abstract problem and architectural finding

For pre-state `S`, post-state `S'`, the contract requires
`R1(S,S') AND R2(S,S')`, not a choice of one transition or a semantic
interpretation of serialization order. Before R5.18, `_relational` in
`benchmark/semantic/generative_r5_13.py` claimed each collection projection
once (`collection_changes` set) and rejected its second claimant. This is a
one-relation-per-collection *transition ownership* restriction, not missing
type binding or a missing core construct. The emitter then walked the input
list procedurally, and the case verifier checked each default separately
against the original population; merely removing the guard would fail joint
conformance. Scalar equality was already allowed on a distinct state field.

## Typed classification and supported subset

| Overlap | Classification | R5.18 decision |
| --- | --- | --- |
| Same uniquely keyed collection; distinct optional fields; values read only from input/pre | independent compatible | compose N, any positive N |
| Identical collection, key, field and expression | redundant | deduplicate in plan |
| Same field, distinct typed literal defaults | direct conflict | `CONFLICTING_RELATIONS` before generation |
| Same field, distinct nonliteral expressions | unresolved equivalence/read-write risk | explicit unsupported rejection |
| Different key bindings on one collection | incompatible identity assumptions | explicit unsupported rejection |
| Fresh insertion and default on one collection | collection-structural overlap | explicit unsupported rejection |
| Normalization of a written field or other collection transform | order/dependency overlap | unsupported; no inferred execution order |
| Equality on separate envelope field plus defaults on collection | independent projections | supported |

Other relation classes (including arbitrary ordered insertion, same-field
normalization and mutation, and general post-state-dependent expressions) are
not certified by this plan. A distinct typed record-valued result, trim and
cardinality on pre-population also compose with this supported transition.

The compiler validates projection, optional-field type, unique string key
binding and value expression; it groups defaults by `(collection, field)`,
rejects conflicting ownership and sorts the deduplicated plan by typed
projection/field. The plan is compiler metadata, not a new semantic operator.
For each original row `r`, the joint witness retains its identity and all
unrelated fields, inserts `field_i = value_i(input,S)` only where absent, and
retains existing values otherwise. It keeps all old rows, other collections
and unrelated envelope fields. Disjoint field writes and expressions bound
exclusively to input/pre prove pairwise commutation for this restricted class:
applying default A then B equals B then A. The Python backend currently emits
the canonical sequence of individually checked maps, which therefore has the
same joint post-state; the verifier accumulates all defaults into *one*
expected population before comparing full rows (unordered keyed semantics).
Emission does not let a later map undo an earlier distinct-field write.

## Independent generative evidence

`test_relation_composition_r5_18.py` uses an instrument inventory with
`serial`, `model`, `remarks`, optional `calibration`, `cabinet`, `custodian`,
and durable `edition`, `instruments`, `facility`. Its four-entry population
contains neither first/second field, first only, second only, and both, with
unrelated fields and a third optional field. One, two and three defaults run
through the **same** lowerer: exact existing values, identity, unrelated rows,
model/remarks and facility persist, missing values appear. Reversed semantic
relation order gives identical observed public result/durable state and, here,
identical generated bytes. Reordered *output records* still pass the semantic
verifier: no storage-order rule was introduced.

An equivalent duplicate produces the same generated artifact and conformant
execution. Two opposing literal defaults reject in both serializations before
generation. A distinct-expression same-field example and a frame/default
collection overlap reject explicitly. No arbitrary choice of default occurs.
Changing only the semantic set adds a third default, removes a default and
changes a literal default; regeneration changes durable fields accordingly
without editing lowering code. Version `old` transitions to `new`; already
`new` takes a no-write branch. A two-row case reports `{migrated: 2}` even
when more than two fields are filled. Zero-row and four-row populations also
ground and conform; #30 counts the *pre-population*, not field writes.
The record-valued outcome includes that count and a trimmed receipt, using
existing generative expression classes alongside the version transition.

`observe` reads pre-bytes, invokes generated Python as a subprocess, captures
public stdout/exit, and independently reads post-bytes. `challenge` checks
invocation, internal pre/post/outcome/write event against those observations
and verifies artifact/runtime/contract digests. Normal cases ground and pass
the source contract's conjunction. In a disposable artifact with recomputed
integrity manifest, an injected wrong second default faithfully executes:
grounding passes but conformance fails although the first and third defaults
remain correct. Thus R1 alone cannot pass R1 AND R2. Integrity recomputation
is a controlled fault experiment, not evidence of adversarial provenance.

## Planning, portability and boundaries

Typed path/identity checks, conflict analysis, deduplication and canonical
relation plan are target-independent; `expression`/`render` and the generated
list/dict mappings are Python-specific. The plan makes order independence
visible, reduces accidental double writes and gives future backends a bounded
contract to consume; it is not a general dependency optimizer. This helps
deterministic inspection and AI reasoning but cannot settle semantic
equivalence of arbitrary expressions. Verifier and compiler share typed AST
validation, so correlated faults remain possible. Finite grounded cases do
not establish universal implementation correctness.
